# AI Civilization — CLAUDE.md

SaaS-проект: цифровой AI-аватар человека (мозг + компаньон). Интерфейс — Telegram Forum: у каждого пользователя своя
приватная группа, топики = роли бота (Foodguide, Job Hunt, Саморазвитие, Дисциплина, Settings).
Этот файл описывает **Модуль 1 «Мозг и Память»** (БД, память, мультиарендность), **Модуль 2 «Telegram-интерфейс, Оркестратор,
проактивность»** (раздел «Реализовано в шаге 3») и **Модуль 3 «Онбординг, расписание проактивности, еженедельный обзор карантина,
дедуп GC»** (раздел «Реализовано в шаге 4»).

Язык: общение и документация — русский; код, комментарии, идентификаторы — English.

## 1. Рабочие договорённости с пользователем
- Сначала план → пользователь утверждает → только потом действия. Без утверждения ничего не создаём и не меняем.
- Всё проверять дважды; не выдавать непроверенное за факт; отмечать, что проверено, а что нет (и чем).
- Отвечать структурированно, на русском.
- **No Blind Coding:** не хватает файлов/контекста для безопасного изменения — остановиться и запросить конкретные файлы.

## 2. Инженерные правила (обязательны)
1. **Fail-Fast & Retry.** Никаких бесконечных `while`/`await`-циклов вокруг сетевых запросов (Telegram, LLM, embeddings).
   Запрос упал → процесс падает → задачу подхватывает очередь (Celery) и повторяет. Таймауты обязательны.
2. **Zero-Hallucination.** LLM не хранит точные числа, инвентарь, расписание. Жёсткие факты — только в PostgreSQL.
3. **Multi-tenant by design.** В каждой таблице `user_id` (в `users` ключ `id` и есть tenant id). Логики «один пользователь» нет.
4. **No Blind Coding** (см. выше).
5. **Единое состояние.** Боты/персоны не имеют своей памяти: читают единый «мозг» (БД) и меняют только System Prompt.

Как БД это обеспечивает (всё покрыто тестами в `tests/`):

| Правило | Механизм |
|---|---|
| Multi-tenant | `user_id` везде + RLS на каждой таблице + составные FK `(user_id, x_id)`: нельзя сослаться на чужую строку |
| Нет «тихой» записи в Core | `core_facts` с `source='approved_review'` требует `pending_facts.status='approved'` (триггер + CHECK) |
| Абсолютная память | факты версионируются (`valid_from/valid_to`), версия неизменяема (триггер), удаление только осознанное |
| Эмоции ИИ не ломают принципы | CHECK: `source='inferred'` ⇒ `priority ≤ 60`; выше — только через карантин и подтверждение |
| Время не от LLM | `events` создаются только `mini_app` / `bot_confirmed` (CHECK); таймзона валидируется как IANA |
| Ни один байт не пропадает | `messages` — источник истины; Outbox со статусами и lease; идемпотентные ключи |

## 3. Архитектура Модуля 1 («3-Tier Memory»)
- **Tier 1 — Core Profile (PostgreSQL, схема `civ`).** Жёсткие факты (`core_facts`), попадают в System Prompt каждого запроса.
  **Emotional Overrides:** `emotional_states` (priority 0–100, всегда с `expires_at`) + `emotional_overrides` (какое состояние
  перекрывает какой принцип). Кто победил — решает SQL-view `civ.effective_principles` (эмоция перекрывает принцип, только если
  её `priority` **строго больше**, состояние `active` и не истекло), а не LLM. Промпт получает принцип с пометкой «временно
  перекрыт состоянием X». Шкала: принципы с `priority ≥ 60` выведенная ИИ эмоция (макс. 60) перекрыть не может.
- **Tier 2 — Episodic Memory (pgvector в том же PostgreSQL).** `episodic_memories`: текст + `vector(1536)` + provenance
  (`source_message_ids`). **LLM-Judge:** скрытый вызов проверяет, что найденные фрагменты содержат ответ; возвращает строгий JSON
  со списком `evidence_ids`, код проверяет, что все id были среди найденных фрагментов; иначе `NO_DATA`. Фантазировать нельзя.
- **Tier 3 — Context Buffer.** Источник истины — таблица `messages` (PostgreSQL). Redis — только быстрый кэш последних 1–3 дней
  (ключ `ctx:{user_id}:{persona_id}`, TTL 72 ч), полностью восстанавливается из `messages`.
- **Outbox (`memory_outbox`).** Задача не удаляется при успехе: статус `done` (после подтверждённой записи/коммита), отдельная
  Celery-таска чистит `done` старше 7 дней. Claim: `SELECT … FOR UPDATE SKIP LOCKED` + lease (`locked_until`); упавший воркер —
  lease истекает, строка с `status='processing'` берётся снова; `attempts ≥ max_attempts` → `dead` (ручной разбор).
  Повтор безопасен: `UNIQUE (user_id, idempotency_key)` в outbox, `pending_facts`, `episodic_memories`.
- **Карантин (`pending_facts`).** Ночной GC не пишет в Core. Он кладёт предложения (факт или эмоциональное состояние,
  `subject`) со статусом `pending`; раз в неделю пользователь отвечает «оставить/удалить»; решение финально (триггер).
  Одобрение — ОДНА транзакция: `pending → approved` + закрыть старую версию (`valid_to`) + вставить новую (`approved_review`).
  Эмоции ИИ с priority > 60 попадают только сюда; подтверждённое состояние получает `source='user_confirmed'`.
- **Социальный граф / ACL («Дипломат»).** `contacts` + `access_grants` (default deny, scope: `emotional_state_label`,
  `calendar_free_busy`, …; грант возможен только контакту) + `diplomat_audit_log` (приложению доступен только SELECT).
  Межтенантный доступ — ТОЛЬКО через будущие `SECURITY DEFINER`-функции (отдельная миграция), которые обязаны проверять
  `contacts.status='accepted'` (ОБЕ строки пары), не отозванный/не истёкший грант и писать аудит (отказ — результатом, а не исключением,
  иначе откат уничтожит запись об отказе). Прямого чтения чужих данных нет. С шага 2 Модуля 5 приложение не может писать в `contacts`:
  связь создаёт только `civ.accept_invite` (см. «Реализовано в Модуле 5, шаг 2»).
- **Расписание (`events`).** Жёсткое расписание из Telegram Mini App; привязка к персоне/топику; серии через RRULE
  (разворачивает код), исключения — строки с `parent_event_id` + `original_start`; видимость `private/busy_only/shared`.

### Реализовано в шаге 2: Celery, Outbox-воркер, GC, LLM-Judge (`src/ai_civ/memory`, `celery_app.py`, `tasks.py`)
- **Перечисление tenant'ов.** Миграция `0002`: `civ.list_tenants()` (`SECURITY DEFINER`, возвращает только `id` и `timezone`,
  право только у `ai_civ_app`). Дальше вся работа с данными — через `tenant_session`.
- **Beat:** ежечасно `dispatch_nightly_gc` (tenant'ам, у которых местное время ≥ `GC_LOCAL_HOUR`, создаёт `compress_day` за их
  «вчера»; ключ `compress_day:<persona>:<date>`, повтор безопасен), каждые 5 мин `drain_outbox` (tenant'ам с открытой работой
  ставит `process_tenant_outbox`), раз в сутки `purge_done_outbox`.
- **Outbox-воркер** (`memory/outbox.py`): claim `FOR UPDATE SKIP LOCKED` + lease; LLM вне транзакции; финал — одна транзакция
  `mark_done` + результаты. **Fencing:** `mark_done`/`fail` действуют только на строку, которая всё ещё `processing` с тем же
  `attempts`; опоздавший воркер получает `LeaseLost`, и его транзакция откатывается целиком. Ошибка → `failed` + backoff через
  `locked_until` (нет колонки `available_at`), исчерпание попыток → `dead` (реаппер `reap_exhausted`). Первая ошибка в пачке
  прерывает прогон (fail-fast), остальные задачи не сжигают попытки. Реализована операция `compress_day`;
  `embed_episode`/`extract_facts` зарезервированы (без обработчика → сразу `dead`).
- **GC** (`memory/gc.py`): сообщения за день → чанки (без усечения) → один вызов Gemini на чанк → embeddings → одна транзакция:
  upsert `episodic_memories` + `pending_facts` + `emotional_states`. Модель ссылается на сообщения короткими `m1..mN`, не uuid.
  Код принимает предложение, только если: ссылки реальны и принадлежат **пользователю** (не ассистенту), `evidence` — дословная
  цитата цитируемого сообщения, число из `value_num` встречается в этой цитате. Остальное отбрасывается с логом. create/update и
  `target_fact_id` определяет код по `core_facts`; в `core_facts` GC не пишет никогда. Эмоция `priority ≤ 60` →
  `emotional_states` (`inferred`, с `expires_at`, overrides к принципам разрешает код); `> 60` → карантин.
- **LLM-Judge** (`memory/judge.py`, `retrieval.py`): поиск top-k по cosine в `tenant_session`; модель видит фрагменты как `F1..Fn`
  и отвечает `{"verdict","evidence_ids"}`. `ANSWER` принимается, только если JSON валиден, `evidence_ids` непуст, без дублей и
  все входят в показанные фрагменты; иначе `NO_DATA`. Нет фрагментов → `NO_DATA` без вызова модели. Ошибки транспорта не
  глотаются (`LLMError`).
- **Fail-fast к Gemini** (`memory/llm.py`): таймаут на каждый запрос, ретраи SDK выключены (`attempts=1`; по умолчанию SDK делает 5),
  пустой/заблокированный ответ — ошибка, размерность embedding проверяется строго.

Поток: сообщение → `messages` (+Redis) → ночью Celery Beat по каждому tenant: claim → LLM (вне DB-транзакции, с таймаутом) →
одна транзакция: upsert эпизода + `INSERT … ON CONFLICT DO NOTHING` в `pending_facts` + `outbox.done`. Ошибка → падение → ретрай.

### Реализовано в шаге 3: Telegram, Оркестратор, проактивность (`src/ai_civ/bot/`, `tasks.py`)
Запуск: `python -m ai_civ.bot` (aiogram 3, **Long Polling**, `allowed_updates=["message"]`). Старт fail-fast: нет `TELEGRAM_BOT_TOKEN` →
`ConfigError` до любых подключений; роль, обходящая RLS → падение; `getMe` проверяет токен. Один процесс = один `Runtime` (БД + Gemini).
- **Tenant на КАЖДОЕ сообщение** (`handlers.TenantMiddleware`): `db.resolve_tenant_id(telegram_user_id=<отправитель>)`, затем чат обязан быть
  `users.forum_chat_id` этого tenant'а (одна группа = один пользователь). Неизвестный отправитель / боты / чужой чат — игнор с логом;
  в личке неизвестному отвечаем инструкцией «создайте группу, включите Темы, добавьте меня админом» (Модуль 5; раньше — его Telegram id для админа),
  зарегистрированному — «пишите в форум».
- **General vs топик:** `thread_of(message) = message_thread_id if is_topic_message else None` (в General Telegram может заполнить
  `message_thread_id` для reply-цепочек; то же правило использует сам aiogram). Топик → `personas.telegram_thread_id` → `persona_id`;
  топик без персоны → подсказка, ничего не пишется и не спрашивается у модели.
- **Транзакция ответа** (`orchestrator.py`): (1) входящее → `messages` ПЕРВЫМ (`ON CONFLICT DO NOTHING` по `uq_messages_user_telegram`);
  (2) персона; (3) промпт одной короткой tenant-транзакцией; (4) Gemini **вне транзакции**, жёсткий `asyncio.wait_for(llm_timeout_seconds)`
  поверх HTTP-таймаута; (5) ответ уходит в топик, **затем** пишется в `messages` (в контексте только то, что пользователь реально
  увидел; неудавшаяся отправка не оставляет «фантомного» ответа). Длинный ответ режется под 4096, в БД хранится целиком.
- **Промпт** (`prompt.py`): system = промпт персоны + Rules + текущее время (считает код, не модель) + A) Core Profile (`core_facts`,
  `valid_to IS NULL`, не принципы; глобальные + факты этой персоны; по priority, лимит `PROMPT_MAX_CORE_FACTS`) + B) принципы из
  `civ.effective_principles`: перекрытый принцип передаётся с пометкой «TEMPORARILY OVERRIDDEN by state X» (кто победил — решает SQL-view,
  не LLM); C) Context Buffer = сообщения ЭТОГО топика за `CONTEXT_HOURS`=72, новейшие `CONTEXT_MAX_MESSAGES`, при превышении
  `CONTEXT_MAX_CHARS` отбрасываются самые старые (новейшее — никогда). Ходы чередуются user/model, диалог всегда начинается с user
  (иначе подставляется нейтральный opener). Значения фактов — одной строкой (значение не может подделать заголовок). Redis-кэш не используется.
- **«General» → топик** (`routing.py`): каждое сообщение из General классифицирует `GEMINI_ROUTER_MODEL` (JSON `intent/code/title/focus`; ему
  показывают список существующих топиков). Код проверяет: `code` по `^[a-z][a-z0-9_]{1,39}$`, не `general`; title ≤ 60, focus ≤ 300, одной
  строкой. Мусор/невалидный ответ → ответ в General (не выдумываем топик); сбой транспорта → системное уведомление. Существующий `code` →
  персона **переиспользуется** (одна активность не даёт два топика; сохранённый prompt/title главнее ответа модели). Новая: persona-строка
  (tx) → `createForumTopic` (без tx) → привязка `telegram_thread_id` + перенос исходного сообщения в персону (одна tx). Отказ Telegram
  (нет права «Управление темами»/не форум) → понятное сообщение; персона без топика достраивается следующим запросом. (Шаг 0: цитата запроса
  в новом топике убрана, в основной чат уходит «Ушёл с этим в «…» ➡️» с кнопкой-ссылкой на топик.) Не-активность → консьерж в General (`persona_id NULL`).
  **Основной топик пользователь может переименовать (у владельца он называется «Чатик»), а Bot API не умеет читать его название, поэтому ни
  один пользовательский текст и промпт не называют его по имени: везде «основной чат»** (проверено тестом `test_user_facing_texts_do_not_hardcode…`).
- **`/setup`**: (Шаг 0 переписал хардкод-список ролей) топик Settings (`personas.SETTINGS_PERSONA`, создаёт код) + 3–4 топика из целей пользователя —
  см. «Реализовано в шаге 0».
- **Отказоустойчивость:** граница `Orchestrator._guarded`: любое исключение внутри одного сообщения → лог с traceback + пользователю
  `Сбой связи с нейросетью. Повторите позже.` в то место, где он писал (топик создать нельзя → отдельный текст); сбой самой отправки уведомления
  только логируется. Глобальный `dp.errors`-хендлер и собственный backoff aiogram для `getUpdates` — polling не падает. Ретраев-циклов в нашем коде нет.
- **Дубли и «потерянные» ответы:** повторная доставка апдейта (тот же `telegram_message_id`) пропускается, если в топике после него уже есть ответ
  ассистента; если процесс умер до ответа — ответ будет (at-least-once). Повтор после маршрутизации не спрашивает роутер заново.
  Порядок: `asyncio.Lock` на (tenant, топик) — два быстрых сообщения отвечаются по очереди (**только в пределах одного процесса бота**).
- **Проактивность** (`proactive.py`, `tasks.py`): `ProactiveTrigger(key, persona_code, instruction)` — инструкция в коде (`TRIGGERS`: `meal_check`→foodguide,
  `work_start`→discipline). `Orchestrator.run_proactive` строит промпт с `is_proactive=True` (секция «Proactive mode», последний ход — системный
  триггер, а НЕ сообщение пользователя и в `messages` не пишется), отправляет в топик персоны через `bot.send_message` и сохраняет ответ как
  `assistant` (ответ пользователя потом видит этот вопрос в контексте). Celery: `ai_civ.send_proactive(user_id, trigger)` (ограниченный autoretry ×3,
  `UnknownTrigger` не ретраится; at-least-once: если отправка прошла, а сохранение упало, повтор может отправить второе сообщение) и
  `ai_civ.dispatch_proactive(trigger, local_hour=None)` (fan-out по tenant'ам, фильтр по ЛОКАЛЬНОМУ часу tenant'а; без autoretry — повтор после
  частичной рассылки дублировал бы напоминания). **В Beat по умолчанию ничего не добавлено** — расписание выбирает пользователь, например
  `{"task": "ai_civ.dispatch_proactive", "schedule": crontab(minute=0), "args": ("meal_check", 13)}`. Ошибки proactive пользователю не показываются.
  (Шаг 4 добавил в Beat расписание ПО ПОЛЬЗОВАТЕЛЯМ — см. ниже; этот хук остаётся для разовых нужд.)

### Реализовано в шаге 4: онбординг, расписание проактивности, обзор карантина, дедуп GC (миграция `0003`, `bot/{onboarding,schedule,review}.py`)
- **Онбординг** (`bot/onboarding.py`, состояние в `users.onboarding_state/step/draft`; `pending → in_progress → done`). Новый tenant (`INSERT` без
  явного состояния = `pending`) НЕ допускается в экосистему: `Orchestrator.handle_message` ведёт интервью в том месте, где человек написал
  (топик не нужен), `/setup` до конца интервью только запускает/повторяет его, `run_proactive` молчит. Строки `users`, существовавшие на момент
  миграции `0003`, считаются прошедшими (`done`). **Фиксированный сценарий из 7 вопросов:** имя/обращение, город → часовой пояс, занятие, стиль
  общения, цели, принципы, подъём/отбой + время напоминаний (еда, начало работы). LLM (`GEMINI_ONBOARDING_MODEL`, вне транзакции, под
  `_bounded`) превращает ОДИН ответ в строгий JSON; **код валидирует** (модель предлагает, код решает): имя и город обязаны дословно встречаться в ответе
  пользователя; часовой пояс — реальная IANA-зона (`zoneinfo`) и показывается на подтверждение; время — `HH:MM`, напоминание не может попасть в тихие
  часы пользователя; ключи фактов строит код (`goal.N`, `principle.<валидный slug>`, дубли slug получают суффикс). Негодный ответ → тот же вопрос
  повторяется, ничего не пишется; сбой Gemini → стандартное уведомление, состояние не меняется. Пропущенные пользователем времена берутся по умолчанию
  (подъём 08:00, отбой 22:00, еда 13:00, работа = подъём + 1 ч) и в сводке помечены «(по умолчанию)».
  После 7-го ответа — сводка с номерами; «да» (детерминированно, без LLM) завершает, номер пункта переоткрывает именно его и возвращает к сводке.
  Завершение — ОДНА транзакция (`onboarding.finalize`): Core-факты (`source='onboarding'`, глобальные; версионирование: неизменный факт остаётся,
  изменённый получает новую версию, устаревший факт прежнего интервью закрывается), `users.timezone`, `quiet_hours_*`, `proactive_schedule`,
  состояние `done`; затем бот сам выполняет `/setup`. Запись состояния защищена «было/стало» (`save_progress`): параллельное сообщение не затирается.
  Порядок «отправить → сохранить состояние»: при сбое отправки интервью остаётся там, где пользователь его последний раз видел.
  Повторное интервью для существующего пользователя: `UPDATE civ.users SET onboarding_state='pending', onboarding_step=0, onboarding_draft='{}' …`.
- **Расписание проактивности** (`bot/schedule.py`, таблица `civ.proactive_schedule(user_id, trigger_key, local_time, enabled, last_fired_on)`, тихие
  часы `users.quiet_hours_start/end`, могут переходить через полночь). Beat каждые 5 минут → `ai_civ.dispatch_scheduled_proactive`: для каждого tenant
  `claim_due` в ОДНОЙ транзакции (`FOR UPDATE`) выбирает строки, у которых местное время ∈ `[local_time, local_time + PROACTIVE_GRACE_MINUTES)`, и сразу
  пишет `last_fired_on = локальная дата`: параллельные запуски и ретраи не шлют дважды; опоздавшее сверх grace напоминание в этот день пропускается, а не
  приходит поздно; в тихие часы и до конца онбординга не пишем. Не удалось передать в очередь → claim откатывается (`release`), следующий тик повторит.
- **Еженедельный обзор карантина** (`bot/review.py`). Beat ежечасно → `ai_civ.dispatch_weekly_review`: в `REVIEW_LOCAL_WEEKDAY` (вс) после
  `REVIEW_LOCAL_HOUR` (18) по местному времени → `ai_civ.send_review(user_id)`. `ReviewService.send_weekly`: протухшие (> `REVIEW_EXPIRE_DAYS`)
  `pending` → `expired`; продолжает неотправленный батч либо создаёт новый (не чаще раза в 6 дней, не больше `REVIEW_MAX_ITEMS`, пустых батчей нет);
  заголовок + по сообщению на предложение с inline-кнопками «Оставить / Удалить» (топик Settings, если есть, иначе основной чат); `telegram_message_id`
  батча пишется после рассылки (at-least-once: после сбоя повтор может продублировать карточки, повторное решение невозможно).
  Кнопка (`callback_query`, `callback_data="rv:<uuid>:k|d"`, тот же `TenantMiddleware`: tenant — нажавший, чат — его форум-группа) →
  `ReviewService.decide` в ОДНОЙ транзакции под `FOR UPDATE`: «оставить» = `pending→approved` + закрыть старую версию + новая (`approved_review`,
  `source_pending_id`; БД не даст иначе); эмоция → `emotional_states` как `user_confirmed` + overrides по ключам принципов (разрешает код), уже
  закончившееся состояние → `expired`; `change='delete'` закрывает целевой факт; «удалить» = `rejected`. Решение финально (триггер), повторное нажатие
  отвечает «уже обработано»; чужой tenant не видит строку (RLS → «не нашёл»). Когда решены все карточки батча — `closed_at` и «Обзор завершён».
  Сбой решения → всплывающее `Сбой связи…`, ничего не изменено. `allowed_updates` теперь `["message", "callback_query"]` (**бота после обновления перезапустить**).
- **Дедуп GC** (`gc.fact_signature`): предложение не создаётся, если такое же (ключ + значение; числа сравниваются численно) уже `pending` либо отклонено
  в пределах `REVIEW_COOLDOWN_DAYS`; эмоция — если такая же метка уже ждёт решения (отклонённая эмоция может вернуться: это новый эпизод).
  Ночной GC (сжатие дня, извлечение фактов, эмбеддинги) без изменений с шага 2.

### Реализовано в Модуле 4, шаг 1: бэкенд Mini App (`src/ai_civ/web/`), вход из бота
Утверждённый план Модуля 4 (шаги 1–5): бэкенд → API данных (профиль/принципы/события) → Svelte-фронтенд в стиле Telegram → тесты/доки. Здесь — шаг 1.
- **Отдельный процесс** `python -m ai_civ.web` (FastAPI + uvicorn, `WEB_HOST=127.0.0.1`, `WEB_PORT=8080`; наружу его выставляет туннель). Старт fail-fast:
  нет `TELEGRAM_BOT_TOKEN` → `ConfigError` до открытия порта; роль в обход RLS → `RlsNotEnforcedError`. Бот и web падают/рестартуют независимо.
- **Авторизация** (`web/auth.py`, чистая функция): заголовок `Authorization: tma <initData>`. Подпись по документации Telegram: секрет = HMAC-SHA256(`WebAppData`,
  токен бота), хэш по всем полям кроме `hash` (`signature` остаётся в строке), `compare_digest`; повторяющиеся поля, строка > 8 КБ, битый `user`, `auth_date` старше
  `INIT_DATA_MAX_AGE_SECONDS` (86400: initData не обновляется, пока приложение открыто) или из будущего (> 60 с) отвергаются. `user_id` в открытом виде
  (query/body/заголовки) никогда не читается.
- **Tenant:** `authenticate` (`web/api.py`) = подпись → `db.resolve_tenant_id(telegram_user_id)` → `403 not_registered`; онбординг не `done` → `403 onboarding_required`.
  Любой доступ к данным — `async with db.tenant_session(ctx.tenant_id)`. Ответы об ошибке: `{"error":{"code","message"}}`; 401 несёт `WWW-Authenticate: tma`.
  Всё с `Cache-Control: no-store`; `/docs`, `/redoc`, `/openapi.json` выключены.
- **Ручки сейчас:** `GET /healthz` (без подписи), `GET /` (смоук-страница: открывается в Telegram, шлёт initData в `/api/me` и печатает ответ — проверяет всю цепочку
  туннель → URL в BotFather → подпись → tenant → RLS; шаг 4 заменит её сборкой Svelte), `GET /api/me` (имя из Core, `address_as`, `users.timezone`, контекст запуска).
- **Конфиг:** `TELEGRAM_BOT_USERNAME=PerfectPerson_bot`, `MINI_APP_SHORT_NAME=Overview` (дефолты в `config.py` и `.env.example`, валидируются при старте),
  `Settings.mini_app_direct_link` = `https://t.me/PerfectPerson_bot/Overview`. Публичный HTTPS-URL страницы задаётся ТОЛЬКО в @BotFather (на туннель), в `.env` его нет.
- **Вход из бота:** приветствие нового топика Settings (`texts.SETTINGS_GREETING`) с inline-кнопкой «⚙️ Настройки и Память» и команда `/app` (кнопка в том топике, где её
  набрали; до конца онбординга запускает интервью). Кнопка — обычный `url` с Direct Link, НЕ `web_app`: у `InlineKeyboardButton.web_app` в Bot API написано «Available only in
  private chats», в группе она не сработает. У пользователей, у которых Settings уже существовал, приветствия нет — для них `/app`.
- **Не проверено на реальных сервисах:** что Mini App по Direct Link открывается из группы-форума и получает initData (по документации — `chat_type`/`chat_instance`
  присутствуют); Windows + реальный Telegram. Проверено: тесты (подпись, изоляция tenant'ов, RLS-старт) и холостой запуск процесса на реальной БД.

### Реализовано в Модуле 4, шаги 2–4: API данных, фронтенд на Svelte, запуск одной командой
- **Структура `web/`** (бэкенд): `deps.py` (`ApiError`, `authenticate`, `Auth`/`DB`), `api.py` (`/api/me` + подключение роутеров), `facts.py` (версионные записи `core_facts`),
  `profile.py`, `constitution.py`, `schedule.py`, `recurrence.py` (RRULE: чистый модуль). Единая форма ошибки `{"error":{"code","message",...}}` (в т.ч. 422 с `fields`).
- **Версионная правка факта = одна транзакция:** `SELECT … FOR UPDATE` текущей версии → проверка `expected_fact_id` (страница прислала версию, которую видела) →
  `valid_to = now()` у старой → вставка новой (`source='user_manual'`; значения, которые не прислали, копируются из старой). Проигравший параллельный запрос получает
  `409 conflict` с `current_fact_id` (после коммита победителя заблокированная строка перепроверяется БЕЗ новой версии — поэтому «нет строки» перечитывается без блокировки,
  чтобы отличить «удалена» (404) от «заменена» (409)). `fact_source` не расширяли: `mini_app` нет в enum, используется существующий `user_manual`.
- **Профиль** (`/api/profile`): GET (текущие факты кроме принципов + `users.timezone`), `PUT /facts/{key}` (правка существующего; создавать факты Mini App не умеет —
  они приходят из интервью/карантина/бота), `DELETE /facts/{key}?expected_fact_id` (закрыть версию, история остаётся), `PUT /timezone` (только IANA-регион или UTC;
  единственная колонка `users`, которую API трогает; лишние поля → 422).
- **Конституция** (`/api/principles`): GET читает вердикт `civ.effective_principles` (не пересчитывает); `POST` (ключ `principle.<slug>` из слов самого принципа: транслит,
  `_2` при коллизии); `PUT /{key}` — новая версия + **сброс перекрытий в той же транзакции** (`DELETE FROM emotional_overrides WHERE core_fact_id = <старая версия>`;
  само эмоциональное состояние остаётся — оно влияет на Voice, теряет только власть над правилом); сохранение без изменений — no-op (не версионирует и не сбрасывает);
  `POST /{key}/restore` снимает перекрытия без правки текста (идемпотентно); `DELETE`.
- **Расписание** (`/api/events`, `/api/personas`): окно ≤ 400 дней; повторяющееся событие = ОДНА строка с RRULE, разворачивается в часовом поясе самого события (стенные часы
  переживают смену DST); RRULE валидируется до записи (`recurrence.py`: только DAILY…YEARLY, без DTSTART/EXDATE/BYHOUR…, UNTIL только в UTC, правило должно давать даты;
  разворот ≤ 500 вхождений на серию); одно вхождение убирается строкой-исключением (`parent_event_id` + `original_start`, `cancelled`; идемпотентно, гонка → ровно одна строка);
  правка/удаление — оптимистично по `expected_updated_at` (+ `FOR UPDATE`); смена старта/пояса/правила серии удаляет её исключения (`exceptions_reset`); `created_via='mini_app'`;
  `persona_id` проверяется до записи («чужая» тема → 422); ответ несёт `timezone_mismatch` (пояс события ≠ пояс профиля), событие хранит пояс, в котором запланировано.
  **Не сделано:** статусы done/missed.
- **Одно повторение серии** (правка / перенос / удаление; `web/schedule.py`, `OccurrenceSheet.svelte`): изменённое повторение = строка-ИСКЛЮЧЕНИЕ (`parent_event_id` + `original_start`,
  `planned`), убранное = та же строка со статусом `cancelled`. `POST /api/events/{id}/occurrences/override` — ТОЛЬКО создание исключения (тело: `original_start` + изменённые поля
  `title/description/starts_at/ends_at/all_day/visibility/persona_id`; пояс и повторение не принимаются: они у всей серии; передвижение сохраняет длительность, если не прислан `ends_at`;
  `persona_id: null` снимает тему). Если у этого повторения уже есть исключение (изменено на другом устройстве или убрано) — `409` с `exception_id`/`current_updated_at`, а не молчаливая перезапись;
  параллельные запросы упорядочивает `FOR UPDATE` строки серии (`_series_occurrence`): ровно одно создаётся. Уже существующее исключение правится `PATCH /api/events/{exception_id}` со своим
  `expected_updated_at` (пояс/`recurrence_rule` → 400 `exception_field`; убранное → 400 `occurrence_cancelled`). `POST …/cancel` теперь upsert: убирает и ИЗМЕНЁННОЕ повторение
  (исключение → `cancelled`), идемпотентно (`created` = «убрала именно эта операция»). Удаление строки исключения (`DELETE /api/events/{exception_id}`) возвращает обычное повторение.
  `GET /api/events/{id}` отдаёт строку как хранится (нужен, чтобы из исключения открыть всю серию: исключение не несёт данных мастера); `EventOut` получил `series_id`.
  Правка правила/старта/пояса всей серии по-прежнему сбрасывает ВСЕ её исключения (в т.ч. изменённые). UI: тап по повторению серии открывает «Одно повторение» (название, дата/время, видимость,
  тема, заметка; кнопки «Сохранить это повторение», «Вернуть, как в серии» (для изменённых), «Изменить всю серию…», «Убрать только это повторение»); в списке изменённые помечены «✏️ изменено».
  Ограничение формы: событие длиннее суток двигается только целиком через серию (времена шлются, только если их тронули).
- **Напоминания** (`web/reminders.py`, вкладка «Напоминания» 🔔; пункт 3 «Skeptic Review» закрыт): `GET /api/reminders` (пояс профиля, `grace_minutes`, тихие часы, ВСЕ триггеры из
  `bot.proactive.TRIGGERS`: нет строки → время по умолчанию, выключено, `configured=false`; строки ушедших триггеров не видны), `PUT /api/reminders/{trigger_key}` (`local_time`+`enabled`,
  upsert по `uq_proactive_schedule_user_trigger`; неизвестный триггер → 404), `PUT /api/reminders/quiet-hours` (`start`/`end` `HH:MM`, окно может переходить через полночь, `start == end` → 422).
  Название/описание/время по умолчанию триггера живут в `ProactiveTrigger` (`title`, `description`, `default_time`): новый триггер появляется на экране сам. **Инвариант онбординга
  держится в обе стороны:** ВКЛЮЧЁННОЕ напоминание не может лежать в тихих часах (окно `[start, end)`: 22:00 внутри, 08:00 снаружи) — при смене его времени тихие часы СЖИМАЮТСЯ автоматически (с 2026-10-07; 422 `in_quiet_hours` остался только для окна, где сжать нельзя),
  ни при расширении тихих часов (`reminder_in_quiet_hours` + список `conflicts`, 422); выключенное напоминание время помнит и никому не мешает. Обе записи берут `FOR UPDATE` строки `users`,
  поэтому две параллельные правки не ломают правило вместе (тест: ровно одна проходит). `last_fired_on` экран НЕ трогает: смена времени после сегодняшнего срабатывания не даёт второго
  письма за день (UI пишет «Сегодня уже приходило. Новое время заработает завтра»). Всё, что сохранено, подхватывает Beat-диспетчер `claim_due` на ближайшем тике (тест прогоняет настоящий
  `claim_due`). UI: тихие часы — две time-ленты + кнопка «Сохранить» (по одной, потому что пара должна быть согласована); напоминания — переключатель и время сохраняются сразу;

### Реализовано в шаге 5: Tier 2 (эпизодическая память + LLM-Judge) в ответах бота (`memory/{retrieval,judge}.py`, `bot/{prompt,orchestrator}.py`)
- **Место в потоке `Orchestrator._reply`:** после персоны/роутинга, ДО `build_prompt`: `_recall(tenant, inc.text)` → `Memories | None` → `build_prompt(..., memories=)`.
  Запрос — ТОЛЬКО последнее сообщение пользователя (решение пользователя: предыдущий ход ассистента размывает вектор; абстрактное «а как в прошлый раз?» вытягивает
  Context Buffer). Поиск идёт по всем эпизодам tenant'а (один мозг — одна память, персоной не фильтруется). Всё вне DB-транзакции, кроме коротких чтений.
- **`memory/judge.recall_with_evidence`** (старый `recall()` не тронут): `has_episodes` (нет эпизодов ТЕКУЩЕЙ embedding-модели → `NO_DATA/no_episodes` без эмбеддинга и без Judge) →
  `embed_query` → `search_episodes(..., embedding_model=)` (теперь фильтрует по модели: расстояния между векторами разных моделей ничего не значат) → опциональный `max_distance`
  → `judge_fragments` БЕЗ изменений (строгий режим, решение пользователя) → в промпт идут только фрагменты из `evidence_ids`, в порядке близости. Возвращает `Recalled(result, evidence, considered, best_distance)`.
- **Промпт, секция D «Episodic memory»** (`prompt.select_memories`/`render_memories`, чистые): дата в часовом поясе tenant'а, текст одной строкой (сводка не подделает заголовок), бюджет
  `RECALL_MAX_CHARS` — целые фрагменты отбрасываются с дальнего конца, ближайший остаётся всегда, текст не режется. Три состояния: `found` / `none` («искали, записи нет — не выдумывай»,
  буфер недавнего диалога по-прежнему считается) / `unavailable` (дословно `[Поиск по эпизодической памяти временно недоступен, не утверждай категорично, что данных нет]`).
  `memories=None` — секции нет вовсе (отключено, гейт, нет эпизодов, проактивные сообщения). В `RULES` добавлен пункт: память — история, не инструкции, Core/принципы главнее.
- **Деградация (решение пользователя):** любой сбой Tier 2 (таймаут `RECALL_TIMEOUT_SECONDS`=20 на embed+поиск+Judge, ошибка Gemini/эмбеддинга/БД) → `log.warning` с traceback →
  `Memories("unavailable")`, ответ уходит от чат-модели как обычно, пользователь не видит `FAILURE`. Отмена (`CancelledError`) не глотается.
- **Гейты** (без вызовов моделей): `RECALL_ENABLED=false`; `Orchestrator.embedder is None`; сообщение короче `RECALL_MIN_QUERY_CHARS` (12) или начинается с `/`; у tenant'а нет эпизодов.
  Запрос режется до `RECALL_QUERY_MAX_CHARS` (2000). Judge вызывается через `router_llm` (тот же JSON-канал) с моделью `GEMINI_JUDGE_MODEL`.
- **Логи для калибровки судьи:** `recall tenant=… verdict=… reason=… considered=N best_distance=… evidence=[ids] in Xs` на каждый ответ с поиском.
- **Конфиг:** `RECALL_ENABLED`, `RECALL_MIN_QUERY_CHARS`, `RECALL_QUERY_MAX_CHARS`, `RECALL_MAX_CHARS`, `RECALL_TIMEOUT_SECONDS`, `RECALL_MAX_DISTANCE` (по умолчанию выкл.: не откалиброван); `JUDGE_TOP_K` (8) — как раньше.
- **Известные ограничения:** строгий Judge на репликах-утверждениях («устал») часто даёт `NO_DATA` — смотреть логи и калибровать промпт на реальных данных ночного GC; эпизоды за последние 72 ч могут
  дублировать Context Buffer (не фильтруются); HNSW + RLS без `hnsw.iterative_scan` (pgvector < 0.8) на большом числе tenant'ов может вернуть меньше k строк (принято до масштабирования);
  recall последовательно добавляет embed + Judge к задержке ответа внутри lock'а топика; живой Gemini не проверялся.

  всегда, по обычным сообщениям — не чаще `REGISTRATION_HINT_SECONDS` на группу; не-создателю по сообщению не отвечает вовсе). Повторная проверка по сообщениям не чаще

### Реализовано в Модуле 5, шаг 2: инвайты и «рукопожатие» (миграция `0005`, `bot/{invites,social,notifications}.py`)
Поток: A пишет `/connect` в своей группе → одноразовая ссылка `t.me/<bot>?start=connect_<token>` (согласие A = создание ссылки) → B открывает её (личка с ботом, `/start connect_…`) →
«A хочет установить связь. Принять?» (B видит имя A и то, как представится сам) → [Принять] → `civ.accept_invite` → A получает уведомление в топик Settings. **Доступа ни у кого нет**:
гранты — отдельное решение A (шаг 3). «Отклонить» ничего не пишет и A не сообщает; ссылка остаётся рабочей.
- **БД закрыта от прямой записи в `contacts`** (`REVOKE INSERT, UPDATE ON civ.contacts FROM ai_civ_app`; SELECT и DELETE остались): «accepted» больше нельзя объявить самому. Связь возникает
  только в `civ.accept_invite`. Остальные дыры: триггер `access_grants` требует `contacts.status='accepted'` (раньше FK проверял лишь наличие строки; отсутствующий контакт по-прежнему даёт 23503),
  а при уходе контакта из `accepted` его активные гранты отзываются в том же операторе.
- **Все функции `SECURITY DEFINER`, `search_path = civ, pg_temp`, `EXECUTE` только `ai_civ_app`, и «кто звонит» берут ТОЛЬКО из `civ.current_tenant_id()`** (без контекста падают `42704`; аргумента «от чьего имени» нет):
  `create_invite(token_hash, display_name, ttl)` → `created | not_ready | too_many` (онбординг `done` и группа `active`; максимум 5 открытых ссылок, лимит не обходится гонкой — advisory lock);
  `revoke_invites()`; `peek_invite(token_hash)` (только чтение) → `ok | own | already_connected | not_ready | invalid` — «неизвестна / использована / отозвана / истекла / инвайтер вас заблокировал»
  намеренно неразличимы (`invalid`); `accept_invite(invite_id, display_name)` → `connected | already_connected | invalid | own | not_ready`;
  `pending_notification_tenants(limit)`; `purge_social(...)`; внутренняя `lock_pair(a, b)` (EXECUTE нет ни у кого, кроме владельца).
- **Токен в БД не попадает**: 128 бит (`secrets.token_urlsafe(16)`, 22 символа; payload `connect_<22>` ≤ 64), хранится только SHA-256 (`contact_invites.token_hash`, UNIQUE, считает бот). Таблица `contact_invites`
  (RLS для инвайтера; приложение может только SELECT своих), `display_name` (`civ.is_clean_name`: одна строка, 1–40 знаков, без управляющих и bidi-символов) показывается B ДО решения.
  Имя берётся из Core (`address_as` → `name` → имя в Telegram); бот дополнительно чистит (`invites.clean_display_name`).
- **Рукопожатие — одна транзакция.** Порядок блокировок: (1) `lock_pair(me, inviter)` — симметричный `pg_advisory_xact_lock`, поэтому встречные ссылки A→B и B→A сериализуются и не дедлочатся; (2) `FOR UPDATE` строки инвайта;
  (3) `FOR UPDATE` обеих строк `contacts`. Дальше: `INSERT … ON CONFLICT (user_id, contact_user_id) DO UPDATE` (pending→accepted; чужой alias не затирается; **blocked инвайтера не вскрывается** — для B ссылка просто `invalid`,
  а собственный блок B снимает его явное «Принять»), инвайт `used_at/used_by`, строка в `notification_outbox` (`contact_accepted.<invite_id>`, `ON CONFLICT DO NOTHING`). Двойной клик / вторая ссылка между уже связанными /
  двое на одну ссылку — проверено тестами (8 параллельных кликов → ровно 1 `connected`; гонка двоих за одну ссылку → один `connected`, один `invalid`; встречные ссылки ×6 раундов по 4 вызова — без дедлока, ровно одно уведомление).
- **Бот.** Роутер `social` подключён между регистрацией и оркестраторным и использует INNER-middleware (`PrivateTenantMiddleware`: отправитель — зарегистрированный tenant, чат — его личка): не принадлежащие ему апдейты
  (обычный `/start`, групповые сообщения) проходят дальше нетронутыми. Неизвестный в личке → `CONNECT_NEED_ACCOUNT` (инструкция + «откройте ссылку ещё раз»; токен не хранится: таблицы без tenant'а запрещены). Кнопки
  `cn:<invite uuid>:y|n` (41 байт); результат заменяет вопрос (кнопки исчезают); `message is not modified` на повторном клике проглатывается; сбой решения → alert `FAILURE`, ничего не изменено, кнопки остаются.
  `/connect` — обработчик в групповом роутере (через `TenantMiddleware`: замороженная группа его не получит). Отзыв ссылок (`revoke_invites`) есть в БД и `invites.py`, команды/кнопки для него пока нет (будет в «Связях»).
- **Уведомления** (`notification_outbox` + `bot/notifications.py`): сессия B не видит чат A (RLS), поэтому «сообщить A» хранится в outbox A в той же транзакции и доставляется воркером. Жизненный цикл как у `memory_outbox`:
  claim `FOR UPDATE SKIP LOCKED` + lease, fencing (`mark_done`/`fail` действуют, только если строка всё ещё `processing` с тем же `attempts`), backoff (или `retry_after` Telegram), `dead` после 5 попыток, первая ошибка прерывает
  прогон (fail-fast). Берутся только строки получателя с `group_state='active'`, онбордингом `done` и группой — иначе ждут (попытки не сжигаются). Топик Settings удалён → одна попытка в основной чат. Контакт уже удалён → «нечего
  сообщать», строка `done`. Celery: `ai_civ.dispatch_notifications` каждую МИНУТУ (одна индексированная выборка `pending_notification_tenants` по ВСЕМ tenant'ам, а не обход `list_tenants`) → `ai_civ.send_notifications(user_id)`
  (без autoretry: строка и есть состояние повтора); `ai_civ.purge_social` раз в сутки (один оператор на вид: reap/expire/purge/старые инвайты). At-least-once: смерть между отправкой и `mark_done` даст второе такое же сообщение.
- **Конфиг:** `INVITE_TTL_HOURS` (72), `INVITE_PURGE_DAYS`, `NOTIFICATION_*` (lease, backoff, batch, `DISPATCH_LIMIT`=500, `MAX_AGE_DAYS`=30, `DONE_TTL_DAYS`=7).

  (`kind='event_proposal'`, ключ `event_proposal.<id>`) — одна транзакция. Мусор (грязное название, старт в прошлом или дальше года, пустой/суточный+ период) → `22023`.
- **`civ.respond_event_proposal(proposal_id, accept)`**: только получатель (иначе `unavailable`); `lock_pair` → `FOR UPDATE`; исходы `accepted | declined | already_accepted | already_declined | expired | unavailable`
  (пара больше не взаимная/неживая → `unavailable`, статус не меняется). Принятие — ОДНА транзакция: событие у КАЖДОГО (в его `users.timezone`, `busy_only`, `peer_proposal`) + статус + уведомление
  автору (`event_proposal_answer`, payload `{proposal_id, accepted}`, ключ `event_proposal_answer.<id>`; то же при отказе). Решение финально и идемпотентно (8 параллельных «Принять» → одно событие на сторону).
- **`civ.purge_events(draft_ttl_days, proposal_ttl_days)`**: один оператор на вид для ВСЕХ tenant'ов (просроченные открытые → `expired`, решённые старше TTL удаляются). Отдельная функция, а не расширение
  `purge_social` (её сигнатура завязана на тесты). **В Celery подключена в части 3** (ниже).
- **Проверено:** `tests/test_event_proposals_db.py` (права и «кто звонит», запись закрыта для обеих сторон, чужой не читает, все причины отказа одинаковы и ничего не оставляют, грязный ввод, лимиты и гонка
  за лимит, замена просроченного, принятие/отказ/повтор/«отказ после принятия», чужой отвечающий, просрочка, пара перестала быть взаимной, гонки accept×8 и accept×decline, встречные предложения без дедлока,

  уведомления). **Не проверено:** `0008` на рабочей `civ_db` (накатывает пользователь), живой Gemini (вызовет ли модель функции вместо вранья), реальный Telegram.

### Реализовано в v1.1, фича 3: лимит запросов (`bot/ratelimit.py`, `RateLimitMiddleware`)
Решения пользователя (2026-10-04): 20 сообщений в минуту на пользователя; fail-open при недоступном Redis (только warning); уведомление один раз за окно; фиксированное окно 1 минута; голосовое = обычное сообщение; текст уведомления зашит.
- **Redis, фиксированное окно:** ключ `<RATE_LIMIT_KEY_PREFIX>:<telegram user id>:<floor(time/окно)>`; одна транзакция MULTI/EXEC `SET key 0 NX EX 2*окно` + `INCR` — счётчика без TTL быть не может (иначе сбой между командами заблокировал бы пользователя навсегда).
  Уведомление — второй ключ `…:notice` через `SET NX EX`: кто поставил первым, тот и шлёт текст. Превышение (21-е сообщение окна): апдейт ОТБРАСЫВАЕТСЯ до любого хендлера (ни записи в БД, ни эмбеддинга, ни вызова модели, ни скачивания голоса) и пользователь получает
  `texts.RATE_LIMITED` («Превышен лимит запросов. Пожалуйста, подождите») — один раз за окно. Новое окно — счёт с нуля.
- **Fail-open:** любое исключение/таймаут (`RATE_LIMIT_REDIS_TIMEOUT_SECONDS`=1)/мусорный ответ Redis → сообщение проходит; warning в логе не чаще раза в минуту. Клиент подключается лениво — бот стартует и без Redis. Redis по умолчанию — брокер Celery (`RATE_LIMIT_REDIS_URL` его переопределяет).
- **Место:** ВНУТРЕННИЙ middleware роутера оркестратора (после `TenantMiddleware`): считаются только зарегистрированные в активной группе и только сообщения, дошедшие до хендлера (текст, команды, голос; служебные сообщения и боты не считаются). Поэтому лимитер никогда не заставит бота говорить в
  замороженной группе или с чужим, а незнакомцы не тратят ничей лимит. Регистрация и рукопожатие приглашений имеют свои троттлы и здесь не лимитируются. Нажатия inline-кнопок (`callback_query`) не лимитируются.
- **Конфиг:** `RATE_LIMIT_ENABLED`, `RATE_LIMIT_MESSAGES`=20, `RATE_LIMIT_WINDOW_SECONDS`=60, `RATE_LIMIT_REDIS_URL`, `RATE_LIMIT_REDIS_TIMEOUT_SECONDS`, `RATE_LIMIT_KEY_PREFIX`. `build_dispatcher(..., limiter="default")` строит лимитер из настроек (None при выключении), клиент закрывается на `shutdown`.
- **Тесты:** `tests/test_ratelimit.py` (32: лимитер на фейковом Redis с фейковыми часами — 20 пропущено/21-е отброшено/одно уведомление, окна, пользователи, TTL, fail-open на 4 видах ошибок, зависший Redis, мусорный ответ, частота warning; сборка из настроек; весь поток через Dispatcher: нет вызова модели
  и записи для отброшенных, голос и команды считаются, уведомление в тот же топик, служебные сообщения и незнакомцы не считаются, замороженная группа молчит, Redis лежит — бот отвечает; и тест на РЕАЛЬНОМ Redis: те же вердикты и у каждого ключа есть TTL; на живом Redis (6379) он прошёл). Тестовые стеки выключают лимитер (`rate_limit_enabled=False`).
- **Ограничения:** (1) на границе окон возможен всплеск до 2× лимита (свойство фиксированного окна — выбрано пользователем); (2) лимит на пользователя, а не на группу/IP; (3) отброшенное сообщение теряется (его надо отправить заново); (4) при `RATE_LIMIT_REDIS_URL`/брокере без Redis работает fail-open, т.е. защиты нет.

- **Команды** `/dansk` и `/normal` (`Orchestrator.set_mode`, роутер оркестратора, тот же `TenantMiddleware`): меняют режим персоны того топика, где написаны. Подтверждение — фиксированный текст кода, модель не вызывается и в `messages` ничего не пишется:
  `texts.MODE_DANSK_ON` (на датском) / `MODE_NORMAL_ON` (на русском). Основной чат, топик без персоны и системный топик Settings языкового режима не имеют — подсказка `MODE_NO_TOPIC`, ничего не меняется. До конца онбординга — интервью. Повтор команды идемпотентен.
- **Промпт.** `render_system(..., mode=)`/`build_prompt(..., mode=)`: при `immersion_da` секция `IMMERSION_DA` вставляется сразу после `VOICE` (перед часами и данными) и прямо «перекрывает» правило о языке пользователя (в `RULES` оно теперь ссылается на секцию):
  датский A2–B1, живая разговорная речь; при ошибке пользователя в датском — в конце ответа блок `💡 Rettelse: <исправленное> - <краткое пояснение>` (≤ 2 исправлений, мягко, ошибки не выдумывать); прямая просьба о переводе — единственное исключение: перевод + один короткий пример на датском в контексте (с переводом в скобках).
  Режим читается из строки персоны на КАЖДЫЙ ответ (обычный, на вложение, проактивный в топике персоны); основной чат режима не имеет.
- **Инструменты не затронуты:** `save_fact`, `decompose_task`, `create_cards` и остальные предлагаются и работают как обычно (их маркеры — слова пользователя, не режим); фиксированные тексты кода (карточки, подтверждения) остаются на русском.
- **Проверено:** `tests/test_immersion.py` (22: CHECK и ORM, команды через Dispatcher, изоляция тенантов и топиков, промпт только в режиме — ответ/документ/проактив, три инструмента в датском топике), `alembic check`.
  **Не проверено:** живой Gemini (держит ли датский A2–B1, не придумывает ли «ошибки», когда ставит блок `Rettelse`), реальный Telegram; `0015` на рабочей `civ_db`. Ограничения: качество исправлений вероятностное (просьба к модели, не гарантия кода); подтверждения инструментов и карточки остаются русскими.

### Реализовано в v2.0, PR 3.4: саммаризатор ссылок и YouTube, защита от SSRF (без миграции; `bot/fetch.py`, `bot/summary.py`, `Orchestrator._summarize`)
- **Когда срабатывает:** в сообщении пользователя есть ссылка И просьба о пересказе («сделай выжимку», «перескажи», «о чём тут», «summary», «саммари», «tl;dr»…): `summary.detect` (регулярные выражения в коде). Ссылка без просьбы и просьба без ссылки — обычное сообщение; сообщение с вложением идёт по пути вложений;
  читается только ПЕРВАЯ ссылка; `SUMMARY_ENABLED`. Работает и для голосовых (текст уже расшифрован).
- **SSRF** (`bot/fetch.py`; проверка идёт ДО чтения хотя бы байта цели): только `http/https`, без `user:pass@`, порты только 80/443/8080/8443, имена `localhost`/`*.local`/`*.internal`/`*.lan` отвергаются; IP-литерал проверяется сразу (aiohttp литералы не резолвит);
  DNS разрешает СВОЙ резолвер (`PublicOnlyResolver`) до TCP-соединения и отвергает хост, если ЛЮБОЙ из ответов не публичный (loopback, RFC 1918, link-local/метаданные 169.254.169.254, CGNAT, multicast, reserved, IPv6 local/multicast, IPv4-mapped, NAT64/6to4/Teredo);
  aiohttp подключается ровно к проверенным адресам (второго lookup нет — DNS-rebinding бессилен). Редиректы идут вручную (≤ `FETCH_MAX_REDIRECTS`=3), КАЖДЫЙ шаг проходит ту же проверку URL и тот же резолвер (в т.ч. редирект на литерал, `file://`, приватное имя). Один общий дедлайн `FETCH_TIMEOUT_SECONDS`=10,
  потолок `FETCH_MAX_BYTES`=2 МБ (считается ПОСЛЕ распаковки, работает и без Content-Length), только `text/html`/`xhtml`/`text/plain`. Строгая политика зашита по умолчанию (`fetch.POLICY`); параметр `policy` нужен только тестам (петлевой сервер), ни настройка, ни сообщение его не меняют.
- **Текст:** `trafilatura` (в потоке), заголовок из метаданных, кодировка по заголовку, управляющие/bidi-символы вычищаются, `FETCH_MIN_TEXT_CHARS`=100 (меньше — «нет текста»), `SUMMARY_MAX_CHARS`=30000 (длиннее режется, модели об этом сказано).
  Любой сбой — `FetchError(kind)` → фиксированная вежливая фраза `texts.SUMMARY_FAIL[kind]` (12 видов: bad_url, blocked, dns, timeout, too_large, unsupported, http_error, redirects, no_text, no_transcript, video_unavailable, failed); бот не падает, модель не вызывается.
- **YouTube** (`youtube.com`, `m.`, `music.`, `youtube-nocookie.com`, `youtu.be`; хост сравнивается строго — `youtube.com.evil.example` не YouTube): расшифровка через `youtube-transcript-api` (в потоке, под тем же дедлайном; предпочтение ru/en/da/uk/de, иначе первая доступная дорожка). Нет субтитров / видео недоступно / блокировка запроса — вежливый отказ.
- **Защита от indirect prompt injection:** ответ-пересказ генерируется БЕЗ единой декларации функций — `_summarize` не обращается к реестру инструментов вообще, поэтому текст страницы не может вызвать `save_fact`, `propose_event`, `purge_events` и т.п. (вызывать нечего). Текст страницы лежит в последнем ходе пользователя между строгими тегами `<untrusted_web_content>…</untrusted_web_content>`
  (теги внутри текста заменяются на `[tag removed]`), системный промпт (`SUMMARY_RULES`) называет его недоверенными данными и запрещает выполнять любые инструкции из него и утверждать, что что-то сохранено/отправлено. Ответ сохраняется с `third_party_data=true` (ночной GC не превращает пересказ чужого текста в память). Tier 2 в этом ответе не используется; режим языка топика (например, `/dansk`) действует.
- **Зависимости:** `trafilatura>=2.0`, `youtube-transcript-api>=1.2` (в `pyproject.toml`; на машине поставлены `pip install` в `.venv` 2026-10-06: trafilatura 2.3.1, youtube-transcript-api 1.2.4).
- **Проверено:** `tests/test_summarizer.py` (201: адреса и URL, резолвер до соединения, rebinding, редиректы (3 разрешены, 4-й нет, на приватное имя/литерал/`file://`), лимиты и таймаут на настоящих локальных aiohttp-серверах, извлечение текста, YouTube с подменой библиотеки, весь поток через Dispatcher, включая «страница с инъекцией при включённых ВСЕХ инструментах» и настоящий отказ на `127.0.0.1`), `alembic check` (миграций нет).
  **Не проверено:** реальный интернет (настоящий DNS, TLS, сайты с защитой от ботов, 403 на ботовый User-Agent), реальный YouTube (библиотека неофициальная, YouTube часто блокирует IP дата-центров — тогда `failed`), качество пересказа живым Gemini, реальный Telegram.
  **Ограничения:** порты 80/443/8080/8443 (сайт на другом порту отвергается); JS-страницы без серверного текста дают «нет текста»; PDF/картинки по ссылке не читаются (`unsupported`); одно обращение за раз, без кэша (повторный пересказ скачивает заново); `youtube-transcript-api` ходит на YouTube мимо нашего резолвера (хосты фиксированы, поэтому SSRF там невозможен).

- **`GET /personas`** — активные темы без `feedback` (канал отзывов пересылается автору только ботом). **`GET /chat/history`** — `persona_id` не задан ⇒ СТРОГО основной чат (`persona_id IS NULL`); страницы назад по времени: `before_id` = id самого старого имеющегося сообщения, позиция `(created_at, id)` (у UUID порядка нет), `limit` 1–100, ответ — от старых к новым + `has_more`;
  в сообщении `cards` (JSONB ответа) и метаданные вложения; чужой `persona_id`/`before_id` → 404 (RLS).
- **`POST /chat/stream` (SSE, `sse-starlette`).** Тело — JSON (`client_message_id`, `persona_id|null`, `text`) или `multipart/form-data` (+ файл `voice` ИЛИ `attachment`, опционально `attachment_kind`). События: `token {"text"}` (куски), `card {"card"}`, `done {"user_message_id","reply_message_id"[, "user_text" для голоса]}`,
  `error {"error","code"}` — всегда последнее; клиент выбрасывает полученный текст и повторяет с ТЕМ ЖЕ `client_message_id`. Всё, что человек может исправить до модели (пустое сообщение, неизвестная/чужая/feedback-тема, неподдерживаемый файл, 413 на размер, 415 на тип тела), — обычная HTTP-ошибка до старта потока.
  Повтор с тем же `client_message_id` отдаёт сохранённый ответ из БД (одно `token` с полным текстом + `done`) без вызова модели; две одновременные попытки дают один ответ.
- **Фоновая задача** (`AppChatService.open_stream`/`_stream_task`): ответ генерирует `asyncio.Task`, которая держится в `service.tasks` (защита от GC) и открывает СВОИ короткие `db.tenant_session` на каждый шаг (сессий запроса не получает); события идут в очередь, HTTP-ответ только читает её. Клиент пропал — задача доводит ответ и сохраняет его (повтор получит его из БД). Сбой модели/БД на любом этапе: одно событие `error`
  (причина только в логе, не в потоке) и `_abandon` — удаление брошенного сообщения пользователя (если ответа нет; вложение уходит каскадом), чтобы повтор не ждал `app_stale_seconds`. Текст, не прошедший через стрим (текст инструмента, ответ без стриминга), досылается одним `token` (`_unsent_tail`). Таймаут стрима — на КАЖДЫЙ кусок (`llm_timeout_seconds`, для голоса `voice_llm_timeout_seconds`), а не на весь ответ.
  Остановка сервера: `service.aclose()` ждёт задачи в полёте до 30 с.
- **`memory/llm.py`.** Новый протокол `StreamLLM` (`stream_text`) — отдельно от `TextLLM`, чтобы существующие реализации `TextLLM` остались валидными; `GeminiClient.stream_text` на `aio.models.generate_content_stream`: сетевой retry (`_with_network_retry`) только на ОТКРЫТИЕ потока, оборванный посреди поток не повторяется (дублировал бы текст) и даёт `LLMError`; пустой поток — `LLMError`; пустые куски и мысли пропускаются, ведущие пробелы первого куска срезаются. Модель без `StreamLLM` отвечает одним куском.
- **Зависимости:** `PyJWT`, `argon2-cffi`, `sse-starlette`, `python-multipart` (в `pyproject.toml`; в `.venv` поставлены 2026-10-11). `.env.example` дополнен блоком `APP_*`.
- **Проверено:** `tests/app/test_app_api.py` (48 тестов на реальном PostgreSQL с RLS, настоящим FastAPI поверх ASGI, фейковыми Gemini и Redis): полный цикл register → login → `/personas` → refresh → logout, подделанные/просроченные/чужого вида JWT, удалённый пользователь, grace-период (и его конец), 5 параллельных refresh, чужой/поддельный refresh, лимиты (пара, IP, fail-open, `X-Forwarded-For`), SSE `token…done`, повтор без модели,
  одновременные повторы, `error` (в т.ч. посреди потока) с очисткой и успешным повтором, голос/вложение через multipart, ошибки до потока, история (основной чат, страницы, одинаковые `created_at`, карточки, изоляция tenant'ов); на НАСТОЯЩЕМ сокете uvicorn: первый токен у клиента задолго до конца ответа и обрыв клиента посреди потока не теряет ответ. `test_llm.py` (+ тесты `stream_text`: порядок кусков, пустые куски, retry открытия, оборванный поток, ошибка API, пустой поток).
- **НЕ проверено:** живой Gemini (`generate_content_stream` на реальном SDK/прокси: форма чанков, поведение `.text` на нетекстовых частях), настоящее мобильное приложение/сеть операторов (буферизация SSE прокси/CDN: заголовок `X-Accel-Buffering: no` ставит sse-starlette, но Cloudflare/ngrok вживую не гонялись), реальный Redis для лимита авторизации (только фейк; сам лимитер покрыт на живом Redis в `test_ratelimit.py`),
  миграция `0026` на рабочей `civ_db` (накатывает пользователь: `alembic upgrade head`), полный `pytest` (гонялись `tests/app` и соседние наборы).
- **Ограничения:** (1) рассылки (push) и FCM/APNs нет — только `notification_outbox` из `0026`; (2) смена пароля, сброс пароля, подтверждение e-mail, вход через внешнего провайдера не реализованы; (3) refresh-токен в grace-окне размножается (каждое использование — новая сессия), лишние сессии умирают с TTL или `logout`; (4) лимита «сообщений в минуту» для приложения нет (лимит бота действует только в Telegram); (5) сбой после первого токена стирает сообщение пользователя из БД — это осознанно, история не хранит неотвеченных реплик приложения;
  (6) инструменты (`save_fact`, Quick Events и др.) в приложении не подключены (`tools=None`), поэтому `card` пока приходит только из повторов/будущих инструментов.

## 6. Мультиарендность: как работать с БД
- Две роли: **владелец/миграции** (`MIGRATION_DATABASE_URL`, только Alembic, обходит RLS) и **runtime `ai_civ_app`**
  (`DATABASE_URL`, RLS действует). Бот и Celery-воркеры — только под `ai_civ_app`.
- Любой доступ: `async with db.tenant_session(user_id) as s:` — одна транзакция, `set_config('app.user_id', …, true)`.
  Не вызывать `commit()` внутри блока. Без tenant-контекста любой запрос к таблицам падает (fail-fast), а не возвращает пусто.
- Tenant по Telegram id: `await db.resolve_tenant_id(telegram_user_id=… | forum_chat_id=…)` (SECURITY DEFINER, возвращает только uuid).
- На старте приложения/воркера: `await db.verify_rls_enforced()` — падает, если роль обходит RLS (владелец/superuser/BYPASSRLS).
- RLS включён через `ENABLE` (не `FORCE`): владелец таблиц обходит RLS, и именно под ним работают `SECURITY DEFINER`-функции.
  Безопасность держится на том, что приложение подключается НЕ владельцем (см. guard выше).
- View, читаемые приложением, — только `WITH (security_invoker = true)` (иначе view обходит RLS; это проверено тестом).

**Новая таблица — чек-лист:** `user_id uuid NOT NULL REFERENCES civ.users(id) ON DELETE CASCADE`; составные FK
`(user_id, parent_id)` на родителей с `UNIQUE (user_id, id)`; `ENABLE ROW LEVEL SECURITY` + policy `tenant_isolation`
`TO ai_civ_app` (`user_id = (SELECT civ.current_tenant_id())`, USING и WITH CHECK); явный `GRANT` для `ai_civ_app`;
модель в `ai_civ/db/models`; добавить имя в `TENANT_TABLES` (`tests/helpers.py`) — тест `test_every_table_has_user_id_and_rls`
иначе упадёт. Миграция сама падает, если в `civ` осталась таблица без RLS.

## 7. Supabase: особенности (сверено с документацией Supabase)
- Миграции — прямое подключение (порт 5432; IPv6, либо IPv4-add-on) или session pooler (5432, IPv4). Бот/Celery — session pooler или direct.
- Transaction pooler (порт 6543) не поддерживает prepared statements → `DB_POOLER_MODE=transaction` (отключает кэши asyncpg, NullPool).
- Через пулер имя пользователя: `<role>.<project-ref>` (для кастомной роли тоже).
- Роль `ai_civ_app` создаётся миграцией как `NOLOGIN`; пароль и `LOGIN` включает оператор вручную (секретов в миграциях нет).
- Атрибуты роли `postgres` в Supabase (BYPASSRLS и т. п.) документацией не подтверждены — архитектура от них не зависит.
- Схема `civ` не входит в Data API Supabase по умолчанию (по умолчанию открыты `public` и `graphql_public`); `alembic_version` лежит в `civ`.
- asyncpg не понимает `sslmode=` → конфиг сам заменяет на `ssl=`.
- Схема `extensions` по документации Supabase доступна `public` → `ai_civ_app` получает USAGE. Если нет, миграция падает
  (`permission denied for schema extensions` или явное сообщение) и откатывается целиком; лечится
  `GRANT USAGE ON SCHEMA extensions TO PUBLIC` под владельцем схемы (проверено на локальном PostgreSQL обоими путями).
- Windows: в `alembic.ini` задано `path_separator = os` — иначе Alembic режет `prepend_sys_path` по `:`, и путь `D:\…`
  ломается (changelog Alembic 1.16; поведение воспроизведено эмуляцией, на самой Windows не запускалось). SQL-файлы — чистый ASCII,
  файлы читаются с `encoding="utf-8"`.

## 8. Команды
```bash
python -m ai_civ.bot                                 # Telegram-бот (Long Polling); нужен TELEGRAM_BOT_TOKEN
python -m ai_civ.web                                 # бэкенд Mini App (FastAPI) на WEB_HOST:WEB_PORT; тот же токен проверяет подпись initData

celery -A ai_civ.celery_app beat -l info
```
Регистрация автоматическая (Модуль 5, шаг 1, см. раздел «Реализовано в Модуле 5»): пользователь добавляет бота в свою форум-группу, SQL не нужен.
Ручной вариант остаётся для служебных нужд (под владельцем БД): `INSERT INTO civ.users (telegram_user_id, forum_chat_id, timezone) VALUES (<telegram id>,
<id форум-группы, вида -100…>, 'Europe/Copenhagen');` — новая строка получает `onboarding_state='pending'`.
```bash
pip install -e ".[dev]"
alembic upgrade head          # под MIGRATION_DATABASE_URL (владелец)
alembic downgrade base        # схему civ и роль ai_civ_app не удаляет
alembic check                 # модели == БД
alembic upgrade head --sql    # сгенерировать SQL без подключения
pytest                        # нужен TEST_OWNER_DATABASE_URL на ОДНОРАЗОВУЮ БД (тесты делают downgrade base!)
```
Защита тестов: имя БД обязано оканчиваться на `_test`, иначе прогон отказывается стартовать (`CIV_ALLOW_DESTRUCTIVE_TESTS=1` снимает
защиту). Роль `ai_civ_app` общая на весь сервер, тесты задают ей тестовый пароль — на Supabase-проект с данными не направлять.
Новая миграция: `alembic revision -m "..."`; DDL — SQL-файлами в `migrations/sql/<rev>/`, разделитель выражений — строка `--;;`
(тела функций `$$…$$`); в SQL-файлах нельзя писать `:name` (SQLAlchemy `text()` примет за bind-параметр), `::type` можно.
